# Анализ достаточности входов/выходов и выбор основного контроллера

Статус: **черновик** (шаг 3, предварительная проверка ресурсов; пересчёт по уточнённой архитектуре клапанов и RS485-актуаторов)
Основано на: `docs/hardware/periph_distribution.md`, `docs/architecture/modules.md`, `rnd/peripherals.md`, `platformio.ini`

## 1. Требования к I/O (по распределению периферии)

### 1.1. ESP32 (Main Unit) — текущий вариант: NodeMCU V3 (ESP32-DevKitC-like)

#### Управляющие выходы (через драйверы/реле/силовые модули, не напрямую с GPIO)
| Элемент | Кол-во каналов | Текущая конфигурация | Перспектива (прямые GPIO актуаторов) | Примечание |
|---|---:|---:|---:|---|
| Рабочие актуаторы горелки/котла, управляемые ESP32: `ACT_IGNITION_UNIT`, `ACT_OIL_VALVE_MAIN`, `ACT_AIR_VALVE_MAIN`, `ACT_FAN_BLOWER`, `ACT_HEATER_OIL`, `ACT_PUMP_OIL_TRANSFER`, `ACT_PUMP_BOILER` | 7 | 7 | 7 | ESP32 управляет **только рабочими клапанами** (`*_VALVE_MAIN`). `ACT_OIL_VALVE_SAFETY`/`ACT_AIR_VALVE_SAFETY` управляются Nano (safety-gate) и **не** являются GPIO ESP32. Все 220В — только через развязку/силовые модули. |
| `ACT_DAMPER_ACTUATOR` | 0 (прямой GPIO) | 0 | 0 | **Через RS485-устройство** (ESP32 мастер). Прямой GPIO ESP32 не требуется. |
| `ACT_PUMP_FLOOR_1`, `ACT_PUMP_FLOOR_B` | 0 (прямой GPIO) | 0 | 0 | **Через RS485-устройства**. Прямой GPIO ESP32 не требуется. |
| **Итого прямых управляющих каналов ESP32** | **7** | **7** | **7** | Фактическая нагрузка на силовые выходы ESP32 снижена за счёт safety-клапанов Nano и RS485-актуаторов. |

**Вывод:** 7 прямых каналов сейчас и в перспективе по актуаторам горелки/котла. Прямое подключение к GPIO ESP32 недопустимо для 220В — требуется внешняя коммутация (модули реле, твердотельные реле/контакторы с драйверами, либо расширители I/O). При использовании шинных расширителей (I2C MCP23017/PCF8574, SPI shift-регистры) нагрузка на GPIO минимальна. Заслонка и насосы тёплых полов **не увеличивают** число прямых GPIO ESP32 (идут по RS485).

#### Входы и интерфейсы
| Элемент | Интерфейс | GPIO/ресурсы (оценка) | Примечание |
|---|---|---:|---|
| `SEN_FLAME` | Цифровой/аналоговый (qrb1) | 1 (цифровой или ADC) | В ведении ESP32 |
| Детект пропадания питания сети 220В | Цифровой (через оптрон/датчик) | 1 | Требование архитектуры |
| DS18B20 (1-Wire): `SEN_OIL_TEMP_MAIN`, `SEN_TEMP_BOILER_IN/OUT/CORE`, `SEN_TEMP_TA_IN/OUT` (+ 6 перспективных коллекторов) | 1-Wire | 1 (одна шина) или 2 (разнести) | 6 датчиков сейчас, до 12. Требует аккуратной проводки/подтягивающего резистора; при росте числа — возможно несколько шин |
| `SEN_THERMOCOUPLE_K` + MAX6675 | SPI (CS, SCK, MISO) | 3 | **Решение открыто (шаг 3).** Если на ESP32 — нужны 3 пина. MISO только чтение. |
| Связь с Nano (Safety) | **Рекомендуется выделенный UART (TX/RX)** | 2 | Safety-критичный канал (heartbeat/fail-safe). Вариант общей RS485 рассмотрен в `docs/architecture/modules.md`, но **не рекомендуется**. |
| RS485 к доп.устройствам | UART + направление DE/RE (или авто) | 2–3 | Только ESP32. Обычно отдельный UART/трансивер |
| **Итого (без расширителей, текущий минимум)** | — | **~7–10 GPIO** | Зависит от MAX6675 и реализации RS485/1-Wire |

## 2. Оценка достаточности платформ

### 2.1. ESP32 NodeMCU V3 (текущий выбор, `env:esp32_core`)
- **Плюсы:** 3 аппаратных UART (достаточно для Nano + RS485 + отладка при аккуратной настройке), аппаратный SPI/I2C, Wi-Fi/BT (перспектива), много GPIO, поддержка PlatformIO.
- **Ограничения:** часть GPIO имеют ограничения при загрузке (strapping pins), входы-only на некоторых пинах, питание 3.3В логики. Нужна внешняя развязка/драйверы для 220В.
- **Вердикт по I/O:** **достаточно** при использовании внешней коммутации/расширителей. Прямых управляющих каналов актуаторов стало **7** (вместо прежней оценки 9) благодаря разделению рабочих/safety клапанов и переносу заслонки/насосов полов на RS485. Прямых GPIO хватает на интерфейсы (UART/связь с Nano, RS485, 1-Wire, датчики).
- **RS485:** аппаратно поддерживается через UART; нужен трансивер (MAX485/ADM485/ISO-интерфейс) и при необходимости гальваноразвязка.

### 2.2. Arduino Nano (текущий выбор, `env:arduino_safety`)
- **Плюсы:** простой, детерминированный, 5В логика (удобно для части датчиков/оптронов), надёжен для минималистичной логики.
- **Ограничения:** мало GPIO (14 цифровых, 6 из них могут быть аналоговыми; D0/D1 — UART), мало памяти, нет аппаратных преимуществ для множества шин, ограниченная производительность.
- **Риск:** при выборе Nano для `SEN_THERMOCOUPLE_K` (SPI) + выделенный UART + независимые контуры пинов может стать **впритык**. D0/D1 заняты UART — отладка по USB Serial конфликтует с обменом с ESP32.
- **Вердикт по I/O:** **условно достаточно** для минимального набора безопасности (давление, поплавки, 1-Wire температура масла, выделенный UART к ESP32, RESET, safety-gate клапаны, независимый контур ТЭН). Уточнённая модель клапанов (Nano управляет `*_VALVE_SAFETY`) делает требования прозрачнее, но не снимает дефицит при добавлении MAX6675/опций. **Решение по термопаре выхлопа влияет на Nano критично.**

## 3. Рассмотрение KinCony KC868-A6v3 как основного контроллера

Статус: **детальный анализ выполнен** — см. `docs/hardware/kc868-a6v3_analysis.md`
(подтверждённые спецификации, полная карта выводов, риски, обязательные условия применения).

Кратко по подтверждённым данным (официальный пин-лист KinCony + ESPHome-конфиг):
- ESP32-S3-WROOM-1 N16R8, 12 В, DIN, 6 реле 250 В/10 А, 6 опто-входов, 4×АЦП 0–5 В,
  2×1-Wire, RS485, RS232, USB-C (native), DS3231, OLED, сокет LoRa/nRF24, 6 свободных GPIO.
- **Реле и входы подключены через PCF8574 по общей I2C-шине** (реле `0x24`, входы `0x22`)
  вместе с RTC, OLED и ЦАП. Прямых GPIO-выходов на реле нет.
- **Состояние реле не fail-safe при зависании/сбросе ESP32:** PCF8574 не имеет RESET и
  хранит последнее состояние; при программном сбросе реле могут остаться включёнными.
  Драйвер реле не идентифицирован — поведение при подаче питания/просадке 3,3 В не подтверждено.
- **6 реле против 7 прямых актуаторов ESP32** — не хватает одного канала
  (решение: ТЭН через внешний SSR + последовательный контактор Nano).
- **`SEN_FLAME` нельзя вешать на опто-вход PCF8574** — только прямой GPIO через формирователь.
- Схема **именно v3** не опубликована; тип контактов реле, драйвер, параметры опто-входов,
  изоляция/creepage и терминирование RS485 требуют подтверждения.

**Вывод:** как **безусловная замена Main Unit — не рекомендуется**. Допустимо как Main Unit
только при выполнении обязательных условий §7 в `docs/hardware/kc868-a6v3_analysis.md`
(независимый safety-слой Nano, полный power-cycle платы с ограничением броска тока,
независимая блокировка розжига и ТЭН, `SEN_FLAME` на прямом GPIO, таймауты I2C и статус
здоровья в heartbeat, стендовые испытания, схема v3).
Как вспомогательный I/O/RS485-узел или прототип — разумный вариант.

## 5. Опциональный вариант: FPC (влияние на I/O при внедрении)

Статус: **не принят**. Если вариант FPC будет принят (только гибрид, см. `docs/architecture/modules.md`), потребуется пересчёт I/O и схемы:
- **Nano (инварианты):** прямые входы `SEN_FLOAT_MIN/MAX`, `SEN_OIL_TEMP_SAFETY` **сохраняются**. Выходы Nano: независимый cutoff `ACT_HEATER_OIL` **сохраняется/усиливается**; независимая блокировка/останов `ACT_PUMP_OIL_TRANSFER` **обязательна**. Возможны доп. линии safety-gate/ENABLE к FPC и вход `READY/FAULT`.
- **ESP32:** может снизиться число прямых силовых каналов управления ТЭН/подкачкой (если управление уходит на FPC), но появятся линии связи с FPC (binary/RS485-сегмент). Safety не переносится на ESP32/FPC.
- **FPC (новый модуль, при внедрении):** GPIO для драйвера ТЭН, насоса подкачки, опционально `SEN_OIL_TEMP_MAIN`, интерфейс связи; питание/развязка; обязательный аппаратный fail-safe при отсутствии разрешения Nano.
- **Требование:** пересмотреть пин-мап/силовые цепи на шаге 3/4 только в рамках отдельного решения с `schematic-engineer` + `safety-reviewer`.

## 6. Вывод
- **ESP32 NodeMCU V3:** I/O **достаточно**. Прямых актуаторов ESP32 — **7**; заслонка/насосы полов вынесены на RS485. Подходит как Main Unit при внешней коммутации/развязке.
- **Arduino Nano:** I/O **на грани**, но жизнеспособно для минимального набора при аккуратном пин-мапе. Nano явно управляет safety-gate клапанами (`*_VALVE_SAFETY`) и независимыми контурами. Риск возрастает при добавлении MAX6675/опций.
- **Связь ESP32<->Nano:** **рекомендован выделенный UART** (изолированный, детерминированный, fail-safe). Общая RS485 — рискованный вариант для safety-канала.
- **KC868-A6v3:** детальный анализ выполнен; как Main Unit — только при выполнении §7
  (`docs/hardware/kc868-a6v3_analysis.md`), иначе **не рекомендуется**. Не заменяет Nano
  и не решает задачу независимых контуров/safety-gate.
