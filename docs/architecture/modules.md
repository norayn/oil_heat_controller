# Разделение ответственности ESP32 / Safety Unit

Статус: **актуализирован** (уточнение ролей клапанов, RS485-устройства, анализ UART vs RS485 для связи ESP32<->Nano; добавлен анализ варианта отдельного контроллера подготовки топлива FPC — опционально, без ослабления защиты Nano)

## Общие принципы

- **ESP32 Core (Main Unit)** — полностью управляет котлом, теплоаккумулятором, циркуляционными контурами и всеми процессами системы. Несёт основные нагрузки по организации безопасной работы горелки. 
- **Safety Unit (Arduino Nano)** — супервизор/модуль безопасности. Следит по протоколу за работоспособностью ESP32 (heartbeat/таймауты), контролирует аварийные ситуации по своим датчикам, имеет **независимые контуры отключения горелки**, способен **перезагрузить ESP32**. Также имеет **независимые/принудительные контуры** для отключения нагревательных элементов и при необходимости — для дублирующего управления критичными контурами.
- **Два уровня безопасности.** Безопасный код должен присутствовать в ОБОИХ модулях. Защита реализуется совместно, при этом Nano обладает аппаратно-независимыми путями принудительного отключения горелки.
- **Fail-safe по умолчанию.** При потере связи, подозрении на нештатную работу основного контроллера, либо при срабатывании по своим датчикам — Safety Unit переводит систему в безопасное состояние с использованием **собственных, независимых от ESP32 контуров отключения**.
- **Последовательные клапаны (масло/воздух).** На подачу топлива и на подачу воздуха установлено по **2 нормально-закрытых (NC) клапана последовательно**. **Рабочие клапаны** (`ACT_OIL_VALVE_MAIN`, `ACT_AIR_VALVE_MAIN`) в рабочем режиме управляются **ESP32** (логика FSM). **Защитные/safety-gate клапаны** (`ACT_OIL_VALVE_SAFETY`, `ACT_AIR_VALVE_SAFETY`) управляются **Nano**: при подтверждённо безопасных условиях Nano держит их открытыми; при аварии, потере heartbeat, нарушении условий или неопределённости Nano принудительно закрывает их через **собственные независимые контуры**. ESP32 управляет **только 2 из 4** клапанов и **не может обойти** safety-клапаны Nano.
- **Связь ESP32<->Nano (рекомендация).** Базовый вариант — **выделенный point-to-point UART** с heartbeat, CRC, таймаутами и fail-safe. Вариант использования общей шины RS485 рассмотрен в разделе «Анализ UART vs RS485 для связи ESP32 <-> Nano»; для safety-критичного канала супервизии **не рекомендуется** без отдельного обоснования и ревью `safety-reviewer`.
- **RS485 на ESP32 (доп.устройства).** ESP32 использует RS485 для подключения дополнительных устройств (модули тёплых полов, коллекторные/исполнительные узлы). `ACT_DAMPER_ACTUATOR`, `ACT_PUMP_FLOOR_1`, `ACT_PUMP_FLOOR_B` управляются **через RS485-устройства** (ESP32 — мастер); прямые GPIO-выходы ESP32/Nano для этих актуаторов не требуются. Сбой RS485 не должен влиять на защиту горелки (см. раздел «RS485 и протокол для дополнительных устройств»).

## Распределение ответственности

### Основной модуль (ESP32) — `src_esp32/`
Полное управление процессами системы. Основные нагрузки безопасности возложены на ESP32.

**Управление горелкой и розжигом:**
- [ ] **FSM горелки/котла** — полная логика розжига, прогрева, стабилизации, останова, постпродувки.
- [ ] **Управление рабочими исполнительными механизмами горелки** — ESP32 формирует команды и управляет: `ACT_IGNITION_UNIT`, `ACT_OIL_VALVE_MAIN` (рабочий клапан топлива), `ACT_AIR_VALVE_MAIN` (рабочий клапан воздуха), `ACT_FAN_BLOWER`, `ACT_HEATER_OIL`, `ACT_PUMP_OIL_TRANSFER`, `ACT_PUMP_BOILER`. Управление `ACT_OIL_VALVE_SAFETY`/`ACT_AIR_VALVE_SAFETY` **не входит** в обязанности ESP32 (safety-gate Nano). Любые критичные отключения могут быть принудительно выполнены Nano через независимые контуры.
- [ ] **Контроль хода розжига** — последовательность, таймауты этапов, координация поджига с учётом того, что подача топлива/воздуха возможна только при открытом safety-gate Nano и корректной работе системы.
- [ ] **Организация безопасности** — реализация проверок, логики блокировок, защитных переходов в рамках своей логики управления (основной уровень безопасности).

**Теплоаккумулятор и гидравлика:**
- [ ] **Теплоаккумулятор (ТА)** — контроль температур `SEN_TEMP_TA_IN/OUT`, циклы «нагрев/отдача», принятие решений о запуске котла.
- [ ] **Котловой контур** — `ACT_PUMP_BOILER`, контроль `SEN_TEMP_BOILER_IN/OUT/CORE`.
- [ ] **Подкачка масла** — `ACT_PUMP_OIL_TRANSFER` по уровням и логике системы (с учётом ограничений безопасности).
- [ ] **Насосы тёплых полов (перспектива)** — `ACT_PUMP_FLOOR_1`, `ACT_PUMP_FLOOR_B` управляются **через RS485-устройства** (команды от ESP32 по протоколу доп.устройств). Прямых GPIO для этих насосов на ESP32 нет.
- [ ] **Дымовая заслонка (перспектива)** — `ACT_DAMPER_ACTUATOR` управляется **через RS485-устройство** с учётом требований безопасности. Прямого GPIO на ESP32 нет.

**Связь и координация:**
- [ ] **Обмен с Safety Unit** — двусторонний обмен, формирование телеметрии/heartbeat, приём статуса/алармов от Nano, соблюдение формата протокола. Базовый интерфейс — выделенный UART (см. анализ UART vs RS485).
- [ ] **RS485 интерфейс** — реализация интерфейса для подключения дополнительных устройств, управление шиной, приём/передача по протоколу доп.устройств (в т.ч. управление заслонкой и насосами тёплых полов через slave-устройства).
- [ ] **Мониторинг/диагностика** — агрегирование данных, состояния системы, логика отображения/индикации (при наличии).
- [ ] **Планировщик** — логика циклов работы системы отопления.

**Безопасный код в ESP32:**
- [ ] Критичные проверки и защитные переходы должны быть реализованы и в ESP32 (основные нагрузки безопасности лежат на нём). 
- [ ] Весь код ESP32 должен проектироваться по принципу fail-safe.

### Модуль безопасности (Arduino Nano) — `src_avr8/`
Супервизор. Контролирует работоспособность основного контроллера и аварийные ситуации по своим датчикам. Имеет **собственные независимые контуры отключения горелки**, **механизм перезагрузки ESP32**, а также **возможность принудительного отключения ТЭН подогрева масла** через независимые/принудительные контуры при аварии. Управляет **защитными клапанами** `ACT_OIL_VALVE_SAFETY`, `ACT_AIR_VALVE_SAFETY` как safety-gate.

**Супервизия основного контроллера:**
- [ ] **Мониторинг по протоколу** — приём/оценка состояния ESP32, контроль heartbeat.
- [ ] **Таймаут связи/heartbeat** — при превышении таймаута считается, что ESP32 не в порядке. Инициирует защитные действия (включая перевод safety-gate в fail-safe).
- [ ] **Оценка работоспособности** — анализ статуса от ESP32 (нештатные комбинации, отсутствие обновлений) для принятия решения о вмешательстве.
- [ ] **Перезагрузка ESP32** — при определённых условиях (потеря связи/подозрение на зависание/критичное несоответствие состояния) **имеет возможность перезагрузить основной контроллер**. Механизм реализации (аппаратный RESET через транзистор/МОП/реле либо иное решение) должен быть зафиксирован при проработке схемы.
- [ ] **Вмешательство при некорректной работе** — право принудительно перевести горелку в безопасное состояние вне зависимости от команд ESP32.

**Управление защитными клапанами (safety-gate):**
- [ ] **`ACT_OIL_VALVE_SAFETY`** — Nano управляет защитным клапаном топлива через **собственный независимый контур**. В штатном безопасном состоянии Nano может держать клапан открытым (разрешение подачи), но только при выполнении всех условий безопасности и наличии валидного состояния системы; дальнейшая подача в рабочем режиме регулируется `ACT_OIL_VALVE_MAIN` со стороны ESP32. При аварии/потере связи/неопределённости — **немедленное принудительное закрытие** (NC, fail-safe).
- [ ] **`ACT_AIR_VALVE_SAFETY`** — аналогично для защитного клапана воздуха. Nano обеспечивает safety-gate; рабочим клапаном `ACT_AIR_VALVE_MAIN` управляет ESP32.
- [ ] **Приоритет Nano** — состояние safety-клапанов определяется Nano по безопасности и имеет приоритет над любыми намерениями ESP32.

**Независимые контуры отключения горелки:**
Safety Unit должен иметь **собственные, аппаратно/логически независимые контуры отключения горелки**, не зависящие от контуров управления ESP32. К ним относятся (минимум):
- [ ] **Независимая цепь отсечки/разрешения подачи топлива** — собственный контур управления `ACT_OIL_VALVE_SAFETY` (и, при необходимости по схеме, дополнительная аппаратная отсечка силовой цепи), обеспечивающий принудительное перекрытие подачи топлива при срабатывании защиты независимо от `ACT_OIL_VALVE_MAIN`/ESP32.
- [ ] **Независимая цепь отсечки/разрешения подачи воздуха** — собственный контур управления `ACT_AIR_VALVE_SAFETY` (и при необходимости дополнительная отсечка) для принудительной блокировки подачи воздуха независимо от `ACT_AIR_VALVE_MAIN`/ESP32. При необходимости в независимые контуры может входить отключение `ACT_FAN_BLOWER`.
- [ ] **Независимая логика блокировки розжига/работы** — запрет активации розжига/перехода в рабочий режим по критериям Nano, реализованный через независимые силовые/логические контуры.
- [ ] **Приоритет отключения** — срабатывание по любому критичному триггеру Nano приводит к переводу safety-gate/независимых контуров в fail-safe состояние в приоритете над командами ESP32.

**Отключение ТЭН подогрева масла (`ACT_HEATER_OIL`):**
- [ ] **Независимый аварийный контур** — Safety Unit должен иметь возможность принудительно отключить `ACT_HEATER_OIL` через свой независимый силовой контур/ключ при срабатывании критичных защит (перегрев масла по `SEN_OIL_TEMP_SAFETY`, потеря связи/heartbeat, другие аварийные триггеры).
- [ ] **Приоритет над ESP32** — отключение ТЭН подогрева масла по решению Nano выполняется вне зависимости от команд основного контроллера и имеет приоритет защиты.
- [ ] **Fail-safe** — при переходе в аварийное состояние (потеря связи) Nano обеспечивает отключение `ACT_HEATER_OIL`.

**Дублирующее управление циркуляционным насосом котлового контура (`ACT_PUMP_BOILER`) — опция:**
- [ ] **Резервный контур** — при наличии независимого силового канала Nano **может** реализовать дублирующее управление `ACT_PUMP_BOILER`. Цель — предотвратить локальный перегрев котла в случае потери связи/зависания ESP32, когда основной контроллер не в состоянии запустить/удерживать циркуляцию.
- [ ] **Условия срабатывания** — только при потере связи/heartbeat либо при явном подтверждённом отказе ESP32, с учётом текущих температурных условий (при наличии данных от доступных Nano датчиков или по логике fail-safe).
- [ ] **Приоритет и ограничения** — управление насосом со стороны Nano носит исключительно защитный характер, не должно мешать нормальной логике ESP32 при наличии связи. Реализация рассматривается как **опция**, требующая проработки схемы, силовых цепей и обязательной проверки `safety-reviewer`.
- [ ] **Fail-safe** — при неопределённости предпочтение отдаётся безопасному состоянию согласно принципам fail-safe.

**Контроль по своим датчикам (критичная защита):**
Nano контролирует минимальный необходимый набор для независимой аварийной защиты:
- [ ] **Поплавки** — `SEN_FLOAT_MIN` (критический минимум), `SEN_FLOAT_MAX` (отсечка подкачки).
- [ ] **Температура масла (защита)** — `SEN_OIL_TEMP_SAFETY` (дублирующий/выделенный для аварийной отсечки).
- [ ] **Давление воздуха** — `SEN_AIR_PRESSURE` (однозначно в ведении модуля безопасности Nano).
- [ ] **Аварийные отсечки** — обработка всех критичных триггеров с максимальным приоритетом, через независимые контуры.

**Безопасный код в Nano:**
- [ ] Минимальный, предсказуемый, детерминированный код. 
- [ ] Избегать неоправданных `delay()`, использовать таймауты, рассмотреть watchdog.
- [ ] Критичные реакции должны быть максимально быстрыми.

## Размещение датчиков горения/давления/температуры выхлопа

### Текущее распределение по модулям
- **Датчик давления воздуха (`SEN_AIR_PRESSURE`)** — однозначно относится к ведению модуля безопасности (Arduino Nano). Контроль давления воздуха для обеспечения нормального горения и аварийных отсечек реализуется в Safety Unit.
- **Датчик пламени (`SEN_FLAME`)** — оставляется в ведении основного модуля (ESP32) для более прямого контроля за ходом розжига, стабилизации и работы горелки в рамках основной логики FSM.
- **Датчик температуры выхлопных газов (`SEN_THERMOCOUPLE_K` + MAX6675)** — **вопрос пока открыт**. Окончательное решение о размещении будет принято при проработке пин-мапа (шаг 3) с участием **schematic-engineer** и **safety-reviewer**.

### Варианты размещения `SEN_THERMOCOUPLE_K` + MAX6675
Рассматриваются два принципиальных варианта:

#### Вариант 1. Подключение к модулю безопасности (Nano)
**Суть:** термопара K с модулем MAX6675 подключается непосредственно к Arduino Nano. Nano выполняет независимый контроль температуры выхлопных газов и при превышении критических значений формирует аварийные отсечки через свои независимые контуры отключения горелки.

**Плюсы:**
- **Максимальная независимость защиты.** Контроль перегрева дымовых газов не зависит от работоспособности ESP32.
- **Соответствует принципу fail-safe.** При потере связи с ESP32 защита по перегреву выхлопа остаётся активной.
- **Простота реализации независимых контуров отсечки.** Триггеры доступны напрямую в детерминированном контуре Nano.

**Минусы:**
- **Нагрузка на пины/интерфейсы Nano.** Требуется проверка достаточности вводов и наличия свободного SPI-интерфейса под MAX6675.
- **Ограниченность ресурсов Nano** при реализации фильтрации/обработки (хотя для аварийной отсечки достаточно пороговой логики).

#### Вариант 2. Подключение к основному модулю (ESP32)
**Суть:** термопара K с модулем MAX6675 подключается к ESP32. ESP32 осуществляет контроль температуры, передаёт показания/статусы в Safety Unit по выделенному каналу связи ESP32<->Nano для использования в защите.

**Плюсы:**
- **Больше ресурсов ESP32** для фильтрации, усреднения, логирования и более гибкой логики.
- **Меньше нагрузки на интерфейсы Nano.**
- **Удобнее для комплексной логики котла** и интеграции с другими температурами.

**Минусы:**
- **Зависимость от канала связи.** При потере связи/heartbeat Nano не будет иметь прямого доступа к показаниям термопары, что ослабляет независимую защиту по перегреву дымовых газов.
- **Задержка реакции.** Обработка через протокол менее детерминирована для критичной аварийной отсечки.
- **Снижение уровня независимости.** Нарушает желательный принцип максимальной автономности модуля безопасности при критичных защитах.

### Подход к принятию решения
- **Решение откладывается.** Окончательный выбор варианта размещения `SEN_THERMOCOUPLE_K` + MAX6675 будет принят **только на шаге 3 (пин-мап)** с обязательным участием **schematic-engineer** и **safety-reviewer**.
- **Минимальный safety-путь (обязательно при любом варианте):** защита по перегреву выхлопа **не должна деградировать** до варианта «только ESP32 + UART» без доказанного эквивалента. Предпочтение — прямое подключение/обработка на Nano (или эквивалентный независимый путь в Nano) для аварийной отсечки.
- **Если выбран ESP32 (Вариант 2):** обязателен документированный анализ отказов (обрыв/КЗ термопары, fault MAX6675, зависание SPI, потеря/задержка UART или heartbeat, рассинхрон/некорректные данные) и доказательство, что Nano всё равно достигает fail-safe не хуже требуемого уровня (через независимые триггеры, таймауты, safety-gate). Без этого размещение на ESP32 **не утверждать**.
- **Критерий принятия** — приоритет независимой защиты модуля безопасности. Если размещение на Nano технически возможно без критической перегрузки его ресурсов и с сохранением детерминированной реакции — предпочтителен Вариант 1. Любое компромиссное решение — детальное обоснование и обязательное ревью `safety-reviewer` с доказательством сохранения fail-safe.
- **Проверка пинов** — достаточность выводов, доступные интерфейсы (SPI для MAX6675), коллизии и вопросы развязки будут проанализированы при разработке `docs/hardware/pinmap.md`.
- **Показания для координации** — независимо от выбранного варианта, показания температуры выхлопных газов должны быть доступны ESP32 для информационных и координационных целей.

## Матрица ключевых элементов (ориентир)

| Элемент | ESP32 | Nano (Safety) | Примечание |
|---|---|---|---|
| FSM горелки, полное управление процессом | **Основной** | Супервизия/блокировка | Управление основным блоком — ESP32; финальная блокировка/отсечка — Nano |
| Розжиг/постпродувка | **Ведёт** | Контроль допустимости + блокировка | Команды от ESP32, но запрет/отсечка возможны по Nano |
| `ACT_OIL_VALVE_MAIN` (рабочий, NC, последователен с safety) | **Управление в рабочем режиме** | Не управляет рабочим режимом; подача перекрывается safety-gate Nano при аварии | ESP32 управляет только рабочим клапаном топлива |

## Мониторинг основного контроллера, перезагрузка, независимые контуры

### Мониторинг основного контроллера (ESP32)
- **Heartbeat** — периодический обмен между ESP32 и Nano по выделенному каналу связи (базово UART). Nano ведёт таймер последнего валидного heartbeat/пакета.
- **Контроль валидности** — проверка целостности пакетов (формат/CRC), соответствия ожидаемым сообщениям.
- **Сопоставление состояния** — при наличии расхождений между ожидаемым/полученным состоянием или при аномалиях Nano может инициировать защитные действия.
- **Таймаут потери связи** — при превышении `HEARTBEAT_TIMEOUT` Nano расценивает ESP32 как вышедший из строя/неработоспособный и переводит систему в fail-safe (включая закрытие safety-клапанов).

### Механизм перезагрузки ESP32
- **Назначение** — восстановление работоспособности основного контроллера при зависании/потере связи/нештатном состоянии, когда перезагрузка может помочь вернуть управление, при этом **без ослабления защиты**.
- **Инициатор** — **только Safety Unit (Nano)**. Решение принимается на основе: превышения heartbeat-таймаута, многократных ошибок протокола, выявления критичного рассогласования состояний.
- **Способ** — предполагается аппаратный сброс ESP32 через управляемый ключ (транзистор/MOSFET) по линии RESET/EN ESP32, либо иное гальванически-надёжное решение. Точный вариант фиксируется при разработке принципиальной схемы (в связке с `schematic-engineer`).
- **Условия срабатывания** — жёстко ограничены, не должны приводить к блокировке независимых контуров отключения. Даже после инициирования перезагрузки **независимые контуры отключения горелки Nano остаются активными и при необходимости немедленно переводятся в fail-safe** (safety-клапаны закрыты, ТЭН отключён).
- **Fail-safe** — если перезагрузка не привела к восстановлению связи в отведённое время, Nano остаётся в fail-safe состоянии с отключённой горелкой посредством своих независимых контуров.

### Независимые контуры отключения горелки (Nano)
- **Принцип независимости** — контуры отключения, реализующие принудительное прекращение горения/блокировку розжига, должны быть **независимы от логики и силовых контуров управления ESP32**. Предпочтителен подход, при котором срабатывание защиты Nano размыкает силовые цепи safety-клапанов/активации горелки напрямую по своим реле/ключам, либо формирует запрещающее воздействие, не проходящее через управляющие выходы ESP32.
- **Состав (ориентир)** — управление/отсечка `ACT_OIL_VALVE_SAFETY` и `ACT_AIR_VALVE_SAFETY` (safety-gate), при необходимости отключение `ACT_FAN_BLOWER`/блокировка розжига, а также **отключение `ACT_HEATER_OIL`** через отдельный независимый контур. Конкретный состав силовых цепей определяется при проработке схемы, с обязательной проверкой `safety-reviewer`.
- **Триггеры** — потеря связи/heartbeat, потеря пламени (по данным/логике супервизии, с учётом распределения датчиков), `SEN_AIR_PRESSURE` нет/низкое давление, `SEN_FLOAT_MIN` критический уровень, `SEN_OIL_TEMP_SAFETY` перегрев, `SEN_THERMOCOUPLE_K` перегрев дымовых газов (при размещении на Nano или при наличии надёжного независимого канала — решается на шаге 3), иные критичные условия по логике Nano.
- **Поведение** — немедленное срабатывание, детерминированное, приоритетное. После срабатывания переход в безопасное состояние до явного условия восстановления, определённого логикой Nano.

## Анализ UART vs RS485 для связи ESP32 <-> Nano

Рассматривается возможность использовать уже заложенную шину RS485 для связи основного модуля (ESP32) и модуля безопасности (Nano) вместо выделенного UART.

### Вариант A: Выделенный point-to-point UART (базовый)

**Плюсы:**
- **Изоляция домена отказа.** Сбой/шум/«залипание» RS485-устройств (тёплые полы, заслонка, сторонние модули) **не влияет** на канал супервизии и heartbeat.
- **Простота и детерминизм.** Точка-точка, без адресации/арбитража/коллизий, проще таймауты и разбор кадров; меньше кода и состояний в Safety Unit (Nano).
- **Быстрая fail-safe реакция.** Проще гарантировать ограниченное время обнаружения потери связи.
- **Предсказуемая отладка.** Локализация проблем связи между двумя критичными модулями проще.
- **Соответствие принципу минимализма Nano.** Safety Unit не зависит от стека/логики общей шины.

**Минусы/риски:**
- Требуется дополнительная пара проводников (и при необходимости развязка) между модулями.
- Использует UART-ресурсы (на Nano конфликт D0/D1 с USB-прошивкой — организационно решаемо).
- Нет «единой шины» — чуть сложнее монтаж.

### Вариант B: Общая шина RS485 (ESP32, Nano, доп.устройства)

**Плюсы:**
- Потенциальная экономия на проводке/трансиверах при удачной топологии.
- Единый физический интерфейс (концептуально).

**Минусы/риски (критичные для безопасности):**
- **Общий домен отказа.** Неисправное slave-устройство, короткое замыкание линии, некорректная передача, отражения/терминирование, ошибка firmware доп.модуля могут нарушить обмен ESP32<->Nano или затруднить детект потери связи.
- **Многоточечная сложность.** Требуются адресация, дисциплина мастера, обработка коллизий/ошибок, защита от подмены/ложных кадров; возрастает поверхность ошибок в Nano.
- **Детерминизм heartbeat под вопросом.** Задержки из-за опроса других устройств, повторов, занятости шины могут влиять на своевременность heartbeat/алармов, если протокол спроектирован плохо.
- **Нагрузка на Nano.** Nano должен надёжно выделять свои кадры на шумной шине — усложнение кода в критичном модуле.
- **Риск архитектурной связности.** Нарушается желательная изоляция: некритичные RS485-устройства получают физическую возможность влиять на среду safety-канала.
- **Сложнее сертифицировать/ревьюить безопасность.** Больше сценариев отказа и больше требований к `safety-reviewer`/схемотехнике (изоляция, fail-safe таймауты, bus-off поведение).

### Возможные меры снижения рисков (если когда-либо рассматривать RS485 для safety-связи)
- Строгий master-slave, фиксированные слоты/приоритет для Nano, отдельные таймауты safety-обмена.
- Аппаратная/логическая фильтрация, усиленная CRC, последовательные номера, защита от replay/подмены (насколько применимо).
- Гальваноразвязка сегментов, корректная терминация, защита линии, ограничение числа/типа устройств.
- Доказательство, что **любой** отказ шины/устройств приводит Nano к **fail-safe** не хуже, чем при обрыве UART.
- Обязательное отдельное ревью `safety-reviewer` и фиксация в схеме/протоколе.

Даже с мерами риск остаётся выше, чем у выделенного канала.

### Рекомендация
**Рекомендовано: сохранить выделенный point-to-point UART для связи ESP32<->Nano** (с heartbeat, CRC, таймаутами, fail-safe в Nano).  
**RS485 использовать только для дополнительных (некритичных для прямой отсечки горелки) устройств** — заслонка, насосы тёплых полов, коллекторные модули и т.п., с изоляцией ответственности и fail-safe на уровне прикладной логики ESP32/устройств.

Вариант использования общей RS485 для safety-связи **не принимать** на текущем этапе. Пересмотр возможен только при наличии детального протокола/схемы, доказательства детерминизма и fail-safe, и после обязательного утверждения `schematic-engineer` + `safety-reviewer`.

## Детект пропадания питания сети (основной контроллер)

- **Требование** — основной контроллер (ESP32) должен уметь определять пропадание/потерю питания сети 220В.
- **Предпосылка** — котёл вместе с циркуляционным насосом может питаться от UPS, поэтому система продолжит работать при кратковременном пропадании сети, но контроллер должен корректно зафиксировать факт потери основного питания и отреагировать согласно fail-safe логике.
- **Способы реализации (предварительные)** — детектирование через оптрон, трансформатор/выпрямитель + делитель/компаратор, датчик наличия сетевого напряжения, либо иное надёжное решение. Конкретный способ выбирается при проработке схемы (`schematic-engineer`).
- **Достоверность сигнала (обязательно на этапе схемы/реализации):** антидребезг/фильтрация, гистерезис, критерий подтверждённой потери (порог длительности) и критерий восстановления; исключить ложные срабатывания от кратких провалов, где это безопасно и согласовано с UPS.
- **Реакция и fail-safe (фиксируется до реализации):**
  - **Кратковременный провал (ниже порога подтверждения):** не ослаблять защиту; ESP32 может учитывать событие для логики/диагностики, Nano не полагается на этот сигнал для базовой отсечки горелки.
  - **Подтверждённая потеря сети:** ESP32 фиксирует событие (NVM/лог по правилам ошибок) и информирует Nano по выделенному каналу связи. Реакция ESP32 (ограничение режимов, управляемая остановка, запрет пуска) определяется FSM с учётом UPS и **не должна** требовать действий, ослабляющих независимые контуры Nano.
  - **Длительная потеря / переход на ограниченное резервное питание (если применимо):** переход в безопасный/ограниченный режим по заранее определённой политике (таймауты, состояние ТЭН/подкачки/горелки) — **без обхода** Nano safety-gate/независимых cutoff.
  - **Неопределённость сигнала детекта:** трактовать консервативно в рамках политики системы; независимые контуры Nano остаются активны.
- **Согласование с защитой:** Nano **не зависит** от сигнала пропадания сети от ESP32 для аварийной отсечки. Питание/поведение клапанов, драйверов, реле и самого Nano при пропадании сети/работе от UPS должно быть проверено на схеме (NC/fail-safe, гарантии отключения).
- **Ревью:** схемное решение, пороги/таймауты и поведение при UPS — обязательное согласование с `safety-reviewer`.

## Протокол ошибок: коды, уровни угрозы, хранение в памяти

### Общие принципы
- **Единый протокол ошибок** — коды ошибок должны быть унифицированы для обоих модулей (ESP32 и Nano) и зафиксированы в общем месте.
- **Разделение по уровню угрозы (severity levels)** — каждый код ошибки должен иметь уровень критичности, определяющий реакцию системы.
- **Хранение при аварии** — при переходе любого из контроллеров в аварийное состояние он **обязан** сохранить код ошибки, по которому произошёл переход, в энергонезависимую/постоянную память (EEPROM/Flash с сохранением при сбое питания). Сохранение должно происходить до или одновременно с переходом в fail-safe, с минимальной задержкой.
- **Анализ постфактум** — сохранённый код ошибки используется для диагностики после восстановления/обслуживания.
- **Приоритет** — коды критических аварий имеют высший приоритет и определяют немедленный переход в fail-safe.

### Уровни угрозы (предварительная классификация)
| Уровень | Обозначение | Описание | Реакция |
|---|---|---|---|
| **CRITICAL** | Критический | Непосредственная угроза безопасности (потеря пламени, отсутствие давления воздуха, критический перегрев, критический уровень масла). | Немедленная аварийная отсечка через независимые контуры Nano, переход в fail-safe, сохранение кода ошибки в памяти. |
| **HIGH** | Высокий | Серьёзное нарушение (потеря связи/heartbeat, превышение таймаутов протокола, рассогласование состояний). | Инициирование защитных действий, возможная перезагрузка ESP32 (только Nano), переход в fail-safe при невозможности восстановления, сохранение кода ошибки. |
| **MEDIUM** | Средний | Неисправность периферии/сенсора, не приводящая немедленно к опасному состоянию горелки, но требующая внимания. | Блокировка запуска/переходов, ограничение режимов работы, логирование, сохранение кода ошибки при переходе в аварийный режим. |
| **LOW** | Низкий | Некритичное нарушение/предупреждение (временные ошибки связи, некорректные показания не в аварийном диапазоне). | Логирование, индикация, без немедленной остановки горелки при условии отсутствия других критичных триггеров. |

### Где фиксировать протокол ошибок
**Рекомендуемое решение — создать отдельный документ `docs/protocol/errors.md`.**

**Обоснование:**
- **Чёткость и разделение ответственности.** Протокол связи ESP32<->Nano (`docs/protocol/uart.md`) описывает транспорт, кадрирование, heartbeat, валидацию. Протокол ошибок — самостоятельная сущность (коды, severity, хранение в памяти, правила сохранения), логичнее вынести в отдельный файл.
- **Удобство для всех ролей.** `safety-reviewer`, `nano-dev`, `esp32-dev` смогут работать с кодами ошибок независимо от деталей кадрирования.
- **Единый источник правды.** Коды ошибок должны быть общими для обоих модулей и использоваться в `include/common_protocol.h` (либо в отдельном общем заголовке), поэтому их описание лучше держать в `docs/protocol/errors.md` с перекрёстными ссылками на `uart.md` и `common_protocol.h`.
- **Расширяемость.** Проще добавлять новые коды/уровни без раздувания документа по транспорту.

**Предварительное решение:** зафиксировать структуру и классификацию в `docs/protocol/errors.md` (создать при проработке). В `docs/protocol/uart.md` оставить только ссылки на коды ошибок и правила приоритета алармов. В `include/common_protocol.h` разместить общие определения кодов ошибок и уровней severity.

## RS485 и протокол для дополнительных устройств

У основного модуля **ESP32** должен быть модуль связи **RS485** для подключения дополнительных устройств.

### Назначение
- Подключение модулей управления тёплыми полами (существующие/планируемые), коллекторных модулей, дополнительных исполнительных/измерительных узлов.
- Управление **заслонкой** (`ACT_DAMPER_ACTUATOR`) и **насосами тёплых полов** (`ACT_PUMP_FLOOR_1`, `ACT_PUMP_FLOOR_B`) через RS485-slave устройства (без прямых GPIO этих актуаторов на ESP32/Nano).
- Расширение системы без нагружения safety-канала ESP32<->Nano избыточными не-критичными по горелке данными.

### Требования к протоколу (проектируемый)
Протокол работы по RS485 должен быть:
- **Мастер-слейв** — ESP32 выступает в роли мастера шины RS485. Доп.устройства — слейвы с уникальными адресами.
- **Адресация** — индивидуальный адрес каждого устройства на шине.
- **Фреймовая структура** — фиксированный заголовок, адрес, тип команды/ответа, payload, контроль целостности (CRC). Должна исключать ложные срабатывания.
- **Типы обмена** — опрос (poll) по циклу, запрос состояния, установка параметров (при необходимости), чтение температур/статусов, управление насосами/заслонкой и т.п.
- **Таймауты и повторы** — таймаут ответа слейва, ограниченное число повторов, обработка ошибок.
- **Fail-safe по умолчанию на стороне slave-устройств (обязательно):** для каждого RS485-актуатора/исполнительного устройства должно быть зафиксировано **безопасное состояние при потере связи с мастером, таймауте команд, некорректных данных, watchdog-срабатывании, потере питания/неопределённости**. Примеры (уточнить в `docs/protocol/rs485.md` и при выборе устройств): `ACT_PUMP_FLOOR_1/B` — как правило OFF/безопасный останов контура, если иное не обосновано; `ACT_DAMPER_ACTUATOR` — фиксированная безопасная позиция (определить при проектировании дымоудаления, с учётом влияния на котёл). Устройства должны иметь собственный watchdog/tаймаут потери мастера.
- **Детерминизм/надёжность** — учитывается шумовая среда, приоритет минимальной задержки там, где есть влияние на гидравлику, но **никаким образом не должен обходить защиту горелки**.
- **Версионирование** — поле версии протокола.
- **Изоляция ответственности** — сбой на RS485-шине **не должен** приводить к потере работоспособности защитных функций горелки. Защита горелки остаётся в зоне ответственности ESP32 (основной уровень) и Nano (независимые контуры/safety-gate). Управление заслонкой/насосами тёплых полов через RS485 — прикладная логика; при ошибке должно быть **fail-safe по определённым default-состояниям устройств/ESP32**, **без влияния на критичные контуры горелки** (Nano останавливает горелку независимо).
- **Расширяемость** — возможность добавления новых типов устройств без кардинальной переработки протокола.

Конкретные коды команд/формат фрейма, скорости, параметры таймаутов, default-состояния и watchdog для каждого устройства подлежат фиксации в `docs/protocol/rs485.md` (создать при проработке протокола). На текущем этапе зафиксированы только требования и принципиальная архитектура.

## Принципы обмена ESP32 <-> Nano
Детали протокола описываются в `docs/protocol/uart.md` и `docs/protocol/errors.md` (коды ошибок), реализуются в `include/common_protocol.h`. Базовый транспорт — **выделенный UART** (рекомендация, см. анализ UART vs RS485). Ключевые принципы:
- **Двусторонний обмен** — команды/запросы ESP32 и статус/алармы от Nano.
- **Heartbeat** — обязательный. Нарушение — триггер fail-safe в Nano.
- **Валидация** — `startByte`, длина, CRC, проверка границ.
- **Приоритет алармов** — аварийные сообщения Nano обрабатываются с высшим приоритетом. Коды ошибок с уровнем CRITICAL/HIGH имеют наивысший приоритет.
- **Согласованность состояний** — ESP32 и Nano должны иметь консистентное представление о состоянии безопасности.
- **Защита от потери связи** — все критичные переходы должны учитывать отсутствие валидного обмена.
- **Единые коды ошибок** — при уходе в аварию каждый модуль сохраняет соответствующий код ошибки в энергонезависимой памяти для последующего анализа.
- **Любое изменение транспорта/формата** — требует анализа fail-safe и обязательного ревью `safety-reviewer`.

## Вариант (анализ): отдельный контроллер контура подготовки топлива — FPC (подогрев/подкачка)

Статус: **опциональный вариант, решение не принято**. Базовая архитектура (Nano — прямые safety-датчики и независимые отсечки) остаётся действующей. Любое внедрение — только после детальной схемы и обязательного ревью `safety-reviewer` (+ `schematic-engineer`).

### Цель варианта
Вынести в отдельный контроллер (**Fuel Peripheral Controller, FPC**) прикладные функции:
- управление подогревом топлива (`ACT_HEATER_OIL`, локальная логика/ПИД/ограничения);
- управление подкачкой топлива (`ACT_PUMP_OIL_TRANSFER`);
- опционально — локальное чтение `SEN_OIL_TEMP_MAIN` для ПИД.

### Критичные инварианты (НЕ ослаблять)
1. **Nano сохраняет прямое подключение** к `SEN_FLOAT_MIN`, `SEN_FLOAT_MAX`, `SEN_OIL_TEMP_SAFETY` и независимый контроль по ним. Перенос этих датчиков **исключительно** на FPC запрещён.
2. **Nano сохраняет независимый аппаратный аварийный контур** принудительного отключения `ACT_HEATER_OIL` (перегрев по `SEN_OIL_TEMP_SAFETY`, потеря heartbeat/связи, авария, неопределённость). FPC/ESP32/шины не могут обходить этот контур. Последовательный safety-контакт Nano в силовой цепи/питании ТЭН — обязательное требование при реализации варианта.
3. **Nano сохраняет независимую возможность** безопасной блокировки/остановки `ACT_PUMP_OIL_TRANSFER` при аварийных условиях (по уровням/защите/аварии) через **аппаратно-независимый безопасный путь** (например, силовой разрыв/последовательный safety-контакт/разрешающий ключ с fail-safe default OFF). Nano использует прямые `SEN_FLOAT_MIN/MAX`. Иной вариант допускается **только** при наличии схемы, анализа отказов (обесточивание/зависание FPC/Nano/ESP32, обрыв линий, backfeed) и отдельного `APPROVE` от `safety-reviewer`; до этого FPC по подкачке не проектировать.
4. Потеря связи с FPC/ESP32/RS485, зависание FPC, неопределённость сигналов → **fail-safe** (ТЭН OFF, подкачка OFF, запрет опасных действий) через Nano и аппаратные default-состояния. **Никакой опоры безопасности только на FPC/RS485.**

### Что может уйти на FPC (функционально) и что нет
| Элемент | FPC (нормальная работа) | Nano (safety) | Комментарий |
|---|---|---|---|
| `ACT_HEATER_OIL` | Опционально: управление драйвером/ПИД | **Независимый аварийный cutoff (обязательно)** | Включение возможно только при разрешении Nano; Nano разрывает питание/цепь независимо от FPC. |
| `ACT_PUMP_OIL_TRANSFER` | Опционально: логика подкачки | **Независимая аппаратная блокировка/останов по защите (обязательно)** | Nano блокирует подкачку по прямым `SEN_FLOAT_MIN/MAX`, авариям, потере связи через аппаратный путь (fail-safe default OFF, без опоры на FPC/RS485). |
| `SEN_OIL_TEMP_MAIN` | Опционально: локальный ПИД | Наблюдение/не источник аварийной отсечки | Аварийный перегрев — только по `SEN_OIL_TEMP_SAFETY` на Nano. |
| `SEN_OIL_TEMP_SAFETY` | **Нет (запрещено как единственный источник)** | **Прямой вход, основной контроль** | Критичный датчик аварийной отсечки остаётся на Nano. |
| `SEN_FLOAT_MIN/MAX` | Возможно дублирование сигнала *только* после ревью схемы (не для safety) | **Прямые входы, основной контроль** | Протокольные/дублированные данные не заменяют прямую защиту Nano. |

### Варианты подключения FPC
1. **Бинарный:** вход `ENABLE/ALLOW` от Nano (разрешение по безопасности) + выход `READY/FAULT` в систему. Плюсы: простота, понятный fail-safe gate. Минусы: ограниченная телеметрия/команды.
2. **RS485:** команды/телеметрия (ESP32↔FPC, и/или статус). Плюсы: гибкость. Минусы: общий домен отказов/задержки/сложность; **не заменяет** аппаратный safety-gate и независимые отсечки Nano. При использовании — предпочтительно изолированный сегмент и строгие таймауты fail-safe на стороне Nano/силовых цепей.
3. **Гибрид (рекомендованный при внедрении):** **аппаратный/binary safety-gate от Nano** (и силовые cutoff под Nano для ТЭН/подкачки) + RS485 для операционных команд/телеметрии. Safety **не зависит** от RS485.

### Логика разрешений
- **Кто разрешает подогрев/подкачку по безопасности:** Nano (по `SEN_OIL_TEMP_SAFETY`, `SEN_FLOAT_MIN/MAX`, давлению/состоянию системы в рамках своей логики, состоянию связи/аварий) через аппаратный gate/линии разрешения и независимые силовые контуры.
- **Кто запрашивает рабочий режим:** ESP32 (и/или локальная стратегия FPC в пределах разрешения Nano) — только как операционная команда.
- **Приоритет:** Nano > аппаратные cutoff/gate > FPC/ESP32/RS485.

### Целесообразность
- **Плюсы:** разгрузка ESP32, локальный ПИД подогрева, потенциально более простая компоновка возле бака.
- **Минусы:** усложнение схемы, питания, развязки, прошивки; дополнительный контроллер/домен отказа.
- **Риски для безопасности:** ошибочный перенос датчиков/отсечек ослабит независимость Nano; зависимость от связи при неверной реализации. **Митигация:** только гибрид с прямыми safety-датчиками на Nano, независимым cutoff ТЭН Nano, независимой блокировкой/остановом подкачки Nano, fail-safe по умолчанию.

### Рекомендация (Главный Инженер)
**Не внедрять на текущем этапе.** Зафиксировать как опцию после шагов 1–3 и детального пин-мапа/схемы. При принятии решения — реализовывать **только гибридный вариант** с неизменными safety-инвариантами Nano. Любые схемы/протоколы/назначения пинов для FPC — через `schematic-engineer` и обязательный `safety-reviewer`.

## Важные замечания
- **Две области ответственности по безопасности:** ESP32 несёт основные нагрузки безопасности при управлении котлом; Nano — супервизор с собственными независимыми контурами отключения, safety-gate клапанами `ACT_*_VALVE_SAFETY`, возможностью перезагрузить ESP32, независимым отключением `ACT_HEATER_OIL` и (опционально) дублирующим управлением `ACT_PUMP_BOILER` при потере связи.
- **Независимость защитных контуров** — контуры отключения/safety-gate Nano принципиально независимы от контуров управления ESP32. Это обязательное требование архитектуры.
- **Роли клапанов зафиксированы:** `ACT_OIL/AIR_VALVE_MAIN` — рабочие (ESP32), `ACT_OIL/AIR_VALVE_SAFETY` — safety-gate (Nano). Последовательно, NC, fail-safe.
- **Критичные датчики горелки** — `SEN_AIR_PRESSURE` однозначно на Nano для независимой защиты. `SEN_FLAME` оставлен за ESP32 для прямого контроля хода горения. Размещение `SEN_THERMOCOUPLE_K` + MAX6675 не зафиксировано и будет определено на шаге 3 (пин-мап) с участием schematic-engineer и safety-reviewer с приоритетом независимой защиты.
- **RS485-актуаторы** — `ACT_DAMPER_ACTUATOR`, `ACT_PUMP_FLOOR_1/B` управляются через RS485-устройства; прямые GPIO не выделяются.
- **Канал ESP32<->Nano** — рекомендован выделенный UART; общая RS485 для safety-связи не рекомендуется (см. анализ).
- **Безопасный код в ОБОИХ модулях** — реализуется повсеместно там, где есть влияние на безопасность.
- **Пересечение только через протокол/правила безопасности** — прямое управление критичными контурами в обход правил запрещено; ESP32 не управляет safety-клапанами Nano.
- **RS485 изолирован по смыслу** — дополнительные устройства не управляют напрямую критичными контурами горелки; их взаимодействие идёт через ESP32 с учётом общей логики безопасности.
- **Изменения протокола** — правки `include/common_protocol.h`, логики обмена ESP32<->Nano, а также добавление/изменение кодов ошибок требуют согласования с `safety-reviewer`.
- **Хранение ошибок** — при переходе в аварию код ошибки с указанием модуля и уровня угрозы должен быть сохранён в энергонезависимой памяти для последующего анализа.
