# AGENTS.md — oil_heat_controller

## Цель проекта
Разработка безопасного двухмодульного контроллера печи на отработанном масле с теплоаккумулятором и перспективой управления тёплыми полами.

## Архитектура
Проект развёрнут в **VS Code + PlatformIO**, мульти-окружение в одном репозитории.

| Модуль | Платформа | Назначение | Приоритет |
|---|---|---|---|
| `env:esp32_core` (`src_esp32/`) | **Main Unit: KinCony KC868-A6, ESP32-WROOM-32, USB-C + CH340C**. См. `docs/hardware/kc868-a6_analysis.md` §6/§7. Legacy `esp32dev` env сохраняется. | Основной контроллер: логика котла/теплоаккумулятора, FSM, координация, связь с Nano/сетью/RS485. KC868 onboard PCF8574/I2C **не независимый/fail-safe safety path** (latch/reset/brownout/I2C fault). Реле — прикладное управление при Nano hardware safety-gate/cutoff/block-stop. Критичные датчики Nano (`SEN_AIR_PRESSURE`, `SEN_OIL_TEMP_SAFETY`, `SEN_FLOAT_MIN/MAX`) — прямые на Nano. `SEN_FLAME`: baseline SR-B13/S-47 (direct GPIO + изолированный формирователь). Открытые вопросы: `docs/architecture/blockers.md`. | Координация, но **НЕ** замещает защиту |
| `env:arduino_safety` (`src_avr8/`) | Arduino Nano (ATmega328P) | **Модуль безопасности (Safety Unit)**. Независимый контроль, аварийные отсечки, safety-gate, heartbeat-супервизия, hardware cutoffs/block-stop (SR-B4/SR-B18), supervised power-cycle Main Unit (SR-B6). **Не заменяется.** | **Максимальный. Безопасность превыше всего** |

Связь между модулями — **dedicated point-to-point UART** (safety-критичный канал; общая RS485 для safety-связи не рекомендуется). KC868: USB-C + CH340C — debug (не native USB); safety UART — на свободных GPIO (TBD, шаг 3, board test/официальный пин-лист, §7.18). Протокол: `docs/protocol/uart.md`; миграция `include/common_protocol.h` — только с `safety-reviewer`.

Общие заголовки кладутся в `include/` и подключаются обоими окружениями (`build_flags = -I include`).

## Принципы безопасности

> **Главное правило проекта:** безопасность обеспечивает **финальная полевая сборка** (`esp32_core` + Nano). Всё остальное время — личная разработка на реальной установке, где **риски приняты владельцем** и записаны в `docs/safety/accepted_risks.md`. Принятый риск — не блокер и не повод усложнять код.

- **Fail-safe по умолчанию.** При потере связи (таймаут heartbeat), ошибке протокола, неопределённом состоянии — горелка должна переводиться в безопасное состояние (отсечь подачу топлива и воздуха согласно логике Safety Unit).
- **Дублирование критичных проверок.** Критичные по безопасности проверки реализуются в Safety Unit; в финальной сборке Main Unit не может их обойти.
- **Приоритет безопасности в финальной сборке.** Полевая прошивка работает fail-safe. Отладочные сборки (manual, bench-auto) защит не содержат — это их назначение, риск принят.
- **Детерминизм.** В коде Safety Unit избегать неоправданных `delay()`, использовать таймауты, watchdog при необходимости. Критичные реакции должны быть максимально быстрыми.
- **Минимум и проверяемость.** Safety Unit — минималистичный, предсказуемый код. Меньше абстракций там, где цена ошибки высокая.
- **Безопасный код в ОБОИХ модулях.** Критичные по безопасности участки кода есть как в Safety Unit, так и в Main Unit. Оба модуля должны проектироваться с учётом fail-safe принципов.

## Роли агентов и ревью

В проекте используются следующие роли (соответствуют `rnd/agents_init_roles.txt`):

| Роль | Задачи |
|---|---|
| **Главный Инженер** | Архитектура, распределение обязанностей, принятие решений по шагам плана, контроль целостности. |
| **Разработчик ESP32** | Прошивка `src_esp32/`, FSM котла/теплоаккумулятора, логика циклов, обмен с Safety Unit, интеграция периферии ESP32. |
| **Разработчик Arduino** | Прошивка `src_avr8/`, Safety Unit, жёсткий контроль, таймауты, аварийные отсечки. |
| **Инженер-Схемотехник** | Пин-мап, проверка достаточности выводов, развязка, силовая часть 220В, коллизии. |
| **Ревьювер по Безопасности (safety-reviewer)** | Помогает найти ослабление защиты, если его позвать. **Не является обязательным gate.** |

**Правило:** обязательных ревью и блокеров нет. Решения принимает владелец. Если риск принят — он фиксируется в `docs/safety/accepted_risks.md` и не превращается в запрет или в дополнительную проверку в коде.

## Правила для разработки

### Общие
- **Не гадать.** Если неясно про назначение периферии/логику — сверяться с `rnd/peripherals.md` и обсуждать, не имплементировать наугад.
- **PlatformIO multi-env.** Не трогать `build_src_filter` без веской причины. Общий код только через `include/`.
- **Минимальные правки.** Делать точечные изменения, не рефакторить "заодно" критичный код.
- **Консистентность.** Следовать стилю существующего кода в соответствующем модуле.

### Критично
- **Только через пин-мап.** Назначение пинов фиксируется в `docs/hardware/pinmap.md`; при отладке допустимы CANDIDATE-линии, если понятно, что это временно.
- **Протокол — общий контракт.** При изменении `include/common_protocol.h` обновлять `docs/protocol/uart.md`; согласование не требуется, но рассинхрон двух модулей — главный источник «непонятных» отказов.
- **Защита ослабляется только осознанно.** Если снимаются таймауты, проверки пламени/давления/клапанов/поплавков — это фиксируется в `docs/safety/accepted_risks.md`, а не растворяется в коде.
- **Связь = точка отказа.** В полевой сборке потеря UART/heartbeat должна вести к безопасному состоянию. В отладочной — заглушка «всё ОК» (AR-05).
- **220В/силовая часть.** Реле/клапаны/розжиг проектируются с прицелом на безопасное отключение при снятии питания.
